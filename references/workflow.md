# 学术演示文稿精简工作流

用固定的信息流保证准确性，用最少的重复劳动完成毕业答辩、开题/中期评审或组会文献汇报 PPT。页数、目录、图片、公式、流程图和正文构图始终随研究内容变化，不先挑模板再填内容。

## 总流程

```text
一次预检
→ 一次论文解析
→ 全量图表轻索引与条件物化
→ JSON 清单派生简短 Markdown 说明
→ 证据索引、灵活大纲与逐页规格
→ 只深加工入选资产并构建 PPTX / Word / MJS
→ 一次全稿渲染 + 风险页检查 + 一次针对性修复
→ 白名单生成最小客户包
```

工作流采用双轨预算：普通、有文本层的单篇文献组会默认 `lean_single_paper`；答辩、开题/中期、多篇综述、扫描件、复杂公式或高保真任务使用 `balanced_95`。两者的科学、证据、安全、兼容和交付硬门禁完全相同，区别只在页数软预算、模型深读范围和可选润色停止点。用户明确要求先看大纲时才暂停；否则全流程自动连续，不设人工审批门。

## 渐进披露、活跃上下文与工作预算

不要在开局加载全部参考文件。路由与配置阶段只读 `SKILL.md`、匹配的 profile 和 `intake.md`；进入证据、逐页设计、QA、交付时，再分别读取对应参考。将已确认设置、来源哈希、证据定位和逐页决策写入清单与 `deck-spec.json`，后续只带当前阶段需要的摘要、关键证据和待解决问题，不反复粘贴整篇论文、完整工具输出或已关闭的讨论。诊断输出默认保留总数、错误代码和每类前三个代表样例；只有定位失败时再展开。

正常任务采用适度预算，而不是无限润色：一次环境预检、一次机器提取与定向证据阅读、一次叙事规格、一次内部完整构建/渲染、一轮针对性修复，以及一次干净交付重建。`lean_single_paper` 的冷启动目标约 10–18 分钟，18 分钟进入重复劳动诊断，25 分钟后在硬门通过时停止可选润色；活跃上下文通常控制在约 2–3 万 token。`balanced_95` 冷启动仍以约 20–35 分钟为诊断基线，活跃上下文通常约 4–6 万 token。同源结构调整约 5–12 分钟，局部修订约 2–6 分钟。所有数字都是工作诊断与停止策略，不是牺牲质量的硬超时。

仅在以下情况升级受影响阶段：超长或扫描质量差的材料无法可靠定位证据；多源之间存在关键冲突；博士级复杂叙事、三十页以上成稿、十余张核心重绘或多组核心公式确实需要更深处理；科学、结构或视觉硬门禁失败；用户明确要求高保真复原或深度审校。升级前记录原因、范围和预期产物，不把全流程一并加倍。单篇任务超过约 18 分钟、其他冷启动超过约 30 分钟仍未形成首个可检查成稿时，先诊断重复读取、把全部裁图交给模型、逐行构建、多次整稿渲染和一次性脚本；没有复杂度依据时停止扩张并报告明确阻断点。

当核心主张均有证据、科学与视觉硬失败为零、完整成稿已检查一次、目标问题已回修一次、PPT/Word/MJS 同源且客户包通过白名单时停止。第三轮只允许用于仍存在的硬失败，或主题、字体、母版、导航、渲染器等全局变化；轻微留白、像素相似度、无害元数据和边缘字距不触发升级。

## 1. 预检与项目配置

执行 `references/intake.md`：

- 首次构建前先让 Codex 加载 bundled workspace dependencies；仅使用宿主返回的 Node 与 `RUNTIME_NODE_MODULES` 路径，不猜测私有路径，也不从公共 npm 安装 `@oai/artifact-tool`；
- 随后运行 `node scripts/preflight.mjs`，一次报告 Node、PPTX 构建器、图片/PDF/LaTeX 工具及可用回退；环境未变时复用结果，不逐页或逐公式重复探测；
- 复用用户已经给出的时长、页数策略、主题和其他约束；时长未给出时不询问；
- 只询问缺失的页数策略或主题预设，两项都缺失时一次合并询问，已有项不再确认；
- 建立项目目录、源文件清单和 `project-config.json`；
- 对源文件计算稳定标识或哈希，后续输入未变时复用已完成的提取与分析。

主论文或焦点材料、汇报类型、页数策略和主题预设明确后即可继续。时长仅在用户主动提供时作为近似软约束；其他不影响方向的信息采用可撤销假设，不反复确认。

## 2. 一次建立来源、证据与原始素材底座

系统读取焦点来源一次，至少识别问题、缺口、目标、方法、核心结果、验证、贡献、边界，以及关键数字、单位、图、表和公式。共同产出或更新 `source-manifest.json` 与 `evidence-index.json`，再按 profile 生成分析资产：

- `final_defense`：精简的 `thesis-analysis.json`，以及论文原始图片、`figures.manifest.json` 和由其生成的 `论文图片说明.md`；
- `proposal_midterm`：`milestone-analysis.json`；开题记录计划、前期基础、验证路径、风险与里程碑，中期分开保存已批准计划基线、带日期的实际进展、偏差、风险和下一阶段行动；
- `group_meeting_literature`：每篇焦点论文在 `assets/papers/<paper-id>/` 下使用 `scripts/extract-paper-assets.mjs` 先生成完整 caption/page/bbox 轻索引 `paper-assets.json` 与紧凑 `论文图表资产说明.md`；再由主张、方法、比较、稳健性和局限形成候选 ID，只物化/深读候选图表，最后建立 `paper-index.json`。核心公式只作为 `evidence-index.json` 中的入选证据记录，不全文批量转写或编译；
- 所有 profile 均为实际需要的学校品牌、出版信息或其他外部来源建立可检索记录。

通用提取器仅对有文本层且能识别 `Figure/Fig./Table/图/表` 编号图注的 PDF 承诺高覆盖。它做低成本页面裁图：图身默认在图注上方，表体默认在表题下方；一个方向空间不足时只反向降级一次并记录低置信。全部可检出图表都进入轻索引；只有不超过自动阈值 12 的极小集合才默认全部物化，其他论文先形成通常 6–8 个候选，再只物化候选。普通单篇主稿通常使用 3–6 个父图，模型不得逐张深读全量索引。只有入选资产才做标注、拆图、局部放大、OCR、表格重建或忠实重绘；不得批量编译全部公式。扫描件、非常规图注和复杂版面可标记限制或对核心资产定向修正一次，不无限重试。

核心主张必须能指向 PDF 页码、图表号、公式号、数据、项目记录、DOI 页面或可靠外部来源。开题的假设、计划与预期成果不得写成既成结果；中期的“计划—实际”必须同时引用基线与进展证据。文献组会必须区分论文作者的结论、汇报者的综合与汇报者的批判。尚无证据的内容只能作为假设、讨论问题、边界或待办。

## 3. 叙事、逐页规格与大纲

先读取匹配的 profile reference，再建立主线、选择页面和布局。毕业答辩让结果与验证构成主体；开题围绕“为何值得做、要回答什么、如何获得证据、为何可行”；中期围绕“原计划是什么、实际完成什么、偏差为何、如何收敛”；文献组会围绕“为什么值得读、证据说明什么、是否可信、对本组有什么启发”组织。方法只保留理解结果所需的信息。章节数量、目录页、章节过渡页、论文分隔页和导航方式由叙事决定，不采用固定五或六部分，也不按模板或论文数量复制固定章节结构。

每页只执行一次以下决策链：

```text
评委问题
→ 一句话结论
→ 支撑证据
→ 最快且真实的表达形式
→ 适合该证据关系的布局或自由画布
→ 精简上屏文字
→ 自然发言稿与过渡
→ Sources
```

生成 `deck-spec.json` 作为唯一机器事实源，再由它生成 `PPT内容与设计大纲.md`。公式和流程图只有在实际使用、或确有必要记录否决理由时才写入对应字段；普通页面省略未使用字段，不生成长篇“不需要”的解释。

毕业答辩规格必须在首次构建前先通过两类门禁：

- 结构门禁：正式答辩默认 3–6 个主章节，每个主章节有且仅有一张章节首页；章节名来自论文问题与证据主线，不使用“问题与路线”、“答辩备查”等生产内部语言。备查材料位于结束页之后，不进目录、不进导航、不单独设章节首页。
- 科学设计门禁：每张技术页先声明 `relationship_topology`、`visual_focus`、`annotation_plan` 和必要的 `asset_transform`，再将其落实为实际渲染的图、标注、强调或可编辑关系。声明这些规划字段不等于已落实。分支/汇合/反馈不得使用线性流程版式；密集科研图必须选择直接标注、拆图、局部放大或忠实重绘，不得只做 contain 后缩到双栏。

新的文献组会项目同时启用 `group_meeting_v2` 科学内容合同：不固定页序，但必须覆盖为何值得读/研究问题、学生如何理解方法、证据如何生成、至少一个核心发现、可信度或边界，以及证据绑定且真正出现在主稿中的汇报者综合/批判。核心发现必须闭合到 source-author claim、evidence 和 renderer 真正消费的源视觉；纯文字强调不能充当源证据。公式中心型论文至少展示一项核心公式，非公式驱动论文允许零公式；图表与公式均不使用论文总量百分比 KPI。

常规单篇自动页数通常为 10–14 张可见页、16 张软上限，不默认生成目录、章节过渡或可见附录。唯一封面必须在第一页并标明汇报人和日期；总结/讨论放在倒数第二页，唯一学生结束页必须是最后一页。不得把 QA、证据清单、生成状态或交付说明变成老师可见内容。

若 `workflow_mode=outline_first`，在大纲生成后等待用户；否则直接进入构建，不二次确认。

## 4. 入选资产、公式与成品构建

只加工已经进入 `deck-spec.json` 的资产：

- 原始素材保持不变，裁切、标注、拆分、重绘和兼容转换写入对应来源的 `ready/`；
- 数据图表保留可复核的数据与计算；
- 简单关系图使用可编辑 PowerPoint 形状，复杂关系图选择可靠图形工具；
- 页面没有自然匹配的注册布局时，使用自由画布或项目专属构图，不强套模板。

文献组会的论文快照只显示已核验且对当前叙事有用的字段。标题、作者、发表来源、年份、DOI/URL 和文章类型来自论文或可靠出版页面；影响因子与分区仅在确有用途、标明评价体系和年份并能复核时使用。不得把布局库中的示例刊名、作者、日期、关键词、指标或截图带入正式 PPT。

公式统一按 `references/asset-preparation.md` 的单一链路处理，并调用 `scripts/render-formula.mjs`：本机 LaTeX 可用时优先使用，否则自动走 Skill 内置 MathJax 路径 SVG。只渲染入选公式；本机 LaTeX 和内置 MathJax 各最多尝试一次，再做一次 SVG→PNG 兼容切换，不建立无限回退树，也不要求用户为单次汇报安装 TeX。复杂核心公式无法可靠呈现时停止并报告，不把 raw LaTeX 当普通文本输出。

完成资产引用后，按 `deck-spec.json` 的 profile 选择对应资产库。正常路径运行：

```bash
node scripts/build-project.mjs \
  --project-dir <project-dir> \
  --spec <deck-spec.json> \
  --output-dir <internal-build-dir> \
  --stem <短题名_汇报类型> \
  --render
```

它使用同一规格一次生成可编辑 PPTX、精简 Word 发言稿和同名 MJS，并只渲染一份内部 QA 预览。规格、入选资产和核心渲染代码未变时，签名缓存直接复用三个产物；先合并同一批局部修改，再调用一次构建器，不要每改一行就全量构建。只在定向调试时才分别调用 `build.mjs`、`build-speaker-script.mjs` 或 `create-project-builder.mjs`。

项目内容写入 `deck-spec.json`，不要临时生成数百行的项目专用 spec builder、图片提取器、联系表或交付清洗脚本。只有稳定共享组件确实缺少能力时，才修改 Skill 级脚本并加入回归测试。

项目 MJS 嵌入最终项目规格、只引用 `assets/` 相对路径，默认同时重建同名 PPTX 与 DOCX，不读取客户包之外的 deck spec。客户项目 MJS 必须显式标记 `artifact_purpose: production`；`layout_gallery` 仅允许通过底层构建器生成内部布局库，不进入项目 MJS 和交付暂存链路。

中期“计划—实际”页必须覆盖计划基线和当前进展证据；组会多篇比较页的来源必须覆盖参与比较的每篇焦点论文。

## 5. 一次完整 QA、针对性修复与最小交付

执行 `references/qa.md`：

1. 运行 schema、语义、构建和溢出检查；
2. 渲染全稿一次，先看联系表，再对核心结果、公式、表格、复杂科研图、`free_canvas`、密度/裁切风险页以及封面和结束页做全尺寸检查；普通单篇通常最多查看 8 张全尺寸风险页；
3. 修复学术错误、证据断裂、不可读内容、损坏媒体、错误品牌、遮挡、裁切和异常换行；
4. 局部修改后的复查聚焦受影响页及其前后衔接页，普通单篇通常不超过 4 张；若工具只能整稿导出，可以重新生成全稿但不重复逐页审阅。主题、字体、母版、全局间距、导航或渲染器变化才重新进行一次全稿视觉检查；
5. 硬失败为零、重要问题已修复或明确披露后停止。

默认只进行一轮完整检查和一轮针对性修复。仍有硬失败时继续处理硬失败；不得转而反复微调字距、像素相似度、轻微留白、无害元数据或其他不影响理解与交付的细节。若冷启动任务反复超过约 30 分钟，优先定位重复读取、临时脚本、全量素材加工、多次整稿渲染或交付扫描误报，不得以“继续优化”代替根因修复。

完成内部 PPTX 和 Word 的渲染检查后读取 `references/delivery.md`。调用 `scripts/stage-delivery.mjs`，由同名项目 MJS 在空白暂存目录一次重建 PPTX 与 Word，再通过白名单生成客户包。客户包根目录只能包含：`短题名_汇报类型.pptx`、`短题名_汇报类型.mjs`、`短题名_汇报类型_发言稿.docx` 和 `assets/`。名称不加入姓名、日期、版本、`final` 或“最终版”；姓名、导师、学号等已知身份词作为 forbidden terms 参与检查。

`project-config.json`、原始 `deck-spec.json`、大纲、证据索引、分析 JSON、QA 记录、预览、日志和源 PDF 均留在内部工作区。论文图片说明可随 `assets/figures/` 交付；其余素材仅保留本稿实际使用或该 profile 明确要求交付的内容。用户要求不部署时，不复制到 Codex Skills 目录，也不安装或注册。

维护或发布 Skill 时，先运行 `scripts/validate-skill-assets.mjs --profile release --strict`；它已包含规定的测试、确定性 eval 和预发布打包检查。只有实际写出发布暂存目录或压缩包时才再次调用 `package-skill.mjs`，不要单独重复全套测试或 eval；仅在隔离失败、采集耗时或开发某一测试时定向运行对应命令。
