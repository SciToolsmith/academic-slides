# 学术演示文稿精简工作流

用固定的信息流保证准确性，用最少的重复劳动完成毕业答辩、开题/中期评审或组会文献汇报 PPT。页数、目录、图片、公式、流程图和正文构图始终随研究内容变化，不先挑模板再填内容。

## 总流程

```text
一次预检
→ 一次来源索引（本地默认；明确授权时可用 MinerU）
→ 按需 hydrate 证据
→ 一次叙事与逐页规格设计
→ 只制作入选资产并构建 PPTX / Word / MJS
→ 一次全稿检查 + 一次针对性修复
→ 白名单生成最小客户包
```

默认采用这一均衡流程，不额外询问“快速还是精细”。用户明确要求先看大纲时才在阶段 3 暂停；用户明确要求草稿或深度审校时，只调整该阶段的深度，不改变信息流。

## 渐进披露、活跃上下文与工作预算

不要在开局加载全部参考文件。路由与配置阶段只读 `SKILL.md`、匹配的 profile 和 `intake.md`；进入证据、逐页设计、QA、交付时，再分别读取对应参考。只有在用户明确授权 MinerU 上传或提供现成 MinerU 解压结果时读取 `references/mineru-source.md`。将已确认设置、来源哈希、证据定位和逐页决策写入清单、紧凑的 `deck-map.json` 与 `deck-spec.json`，后续只带当前阶段需要的摘要、关键证据和待解决问题。

每个源文件允许进入活跃上下文的完整内容读取最多一次。MinerU raw 只允许 normalizer 读取；agent 不得直接打开完整或节选的 `full.md`、`content_list*.json`、`model`/`layout` JSON、HTML、TeX、DOCX、`blocks.ndjson` 或完整工具输出。首次分析只读 `document-index.json`，之后只能通过 `retrieve-source-evidence.mjs` 按页码、证据 ID、候选资产或关键词 hydrate；局部修复只 hydrate 受影响页及必要的相邻证据。诊断输出默认保留总数、错误代码和每类前三个代表样例，只有定位失败时再展开。

正常任务采用硬预算，而不是无限润色：一次环境预检、一次机器索引与定向证据阅读、一次叙事规格、只加工入选资产、一次完整视觉 QA、一轮针对性修复。整稿 render 最多两次：第一次用于完整视觉 QA；只有全局变化、工具无法局部导出或仍存在硬失败时才使用第二次。干净交付重建若不导出全套预览，不计作完整 render。第二次之后仍有硬失败时停止循环并报告，不进行第三次整稿 render。

冷启动通常以约 20–35 分钟为诊断基线，同源结构调整约 5–12 分钟，局部修订约 2–6 分钟；这些不是牺牲质量的时限。活跃上下文优先控制在能容纳当前阶段事实的范围，通常约 4–6 万 token；超出前先压缩已确认信息和工具日志，不删减支撑核心主张的证据。

仅在以下情况升级受影响阶段：超长或扫描质量差的材料无法可靠定位证据；多源之间存在关键冲突；博士级复杂叙事、三十页以上成稿、十余张核心重绘或多组核心公式确实需要更深处理；科学、结构或视觉硬门禁失败；用户明确要求高保真复原或深度审校。升级前记录原因、范围和预期产物，不把全流程一并加倍。超过约 30 分钟仍未形成首个可检查成稿时先诊断重复读取、全量抽图、逐行构建、多次整稿渲染和一次性脚本；若约 45 分钟仍无实质进展且没有上述复杂度依据，停止扩张并报告阻断点。

当核心主张均有证据、科学与视觉硬失败为零、完整成稿已检查一次、目标问题已回修一次、PPT/Word/MJS 同源且客户包通过白名单时停止。轻微留白、像素相似度、无害元数据和边缘字距不触发升级。

## 单写者与阶段账本

并行只用于互不重叠的调查或产物。每个规范产物在任一阶段只能有一个 owner 写入；其他 agent 只返回页码、候选 ID、发现或补丁建议，不并行重写同一文件。最低所有权如下：

| 规范产物 | 单一 owner |
|---|---|
| `source-manifest.json`、归一化来源索引、`evidence-index.json` | evidence owner |
| profile 分析文件、`deck-spec.json`、`deck-map.json`、大纲 | story owner |
| `figures.manifest.json` 与 `ready/` 资产 | asset owner |
| PPTX、DOCX、项目 MJS | build owner |
| QA 记录与修复清单 | QA owner |

owner 可以在阶段边界显式移交，但同一时刻不得有两个写者。不要让多个 agent 各自通读全文、各写一套 deck spec 或各生成一套成品后再合并。

在内部 `phase-metrics.json` 中记录可观察事实，不编造 token 数。每个阶段至少记录：`phase`、`started_at`、`ended_at`、`wall_seconds`、`owner`、输入/输出字节数、缓存命中、完整来源读取次数、hydrate 的页/块数、入选与实际加工资产数、完整/局部 render 次数、构建次数、失败与升级原因。宿主提供 token 用量时记录真实值；不提供时写 `null`。阶段结束时追加一次，局部修复更新相关计数，不复制完整日志。

## 1. 预检与项目配置

执行 `references/intake.md`：

- 首次构建前先让 Codex 加载 bundled workspace dependencies；仅使用宿主返回的 Node 与 `RUNTIME_NODE_MODULES` 路径，不猜测私有路径，也不从公共 npm 安装 `@oai/artifact-tool`；
- 随后运行 `node scripts/preflight.mjs`，一次报告 Node、PPTX 构建器、图片/PDF/LaTeX 工具及可用回退；环境未变时复用结果，不逐页或逐公式重复探测；
- 复用用户已经给出的时长、页数策略、主题和其他约束；时长未给出时不询问；
- 只询问缺失的页数策略或主题预设，两项都缺失时一次合并询问，已有项不再确认；
- 建立项目目录、源文件清单和 `project-config.json`；
- 在配置中记录来源策略：默认 `local`；只有用户对指定文件明确授权上传时才允许 `mineru`，且远程调用必须另外带 `--confirm-upload`；
- 对源文件计算稳定标识或哈希，后续输入未变时复用已完成的提取与分析。

主论文或焦点材料、汇报类型、页数策略和主题预设明确后即可继续。时长仅在用户主动提供时作为近似软约束；其他不影响方向的信息采用可撤销假设，不反复确认。

## 2. 一次建立来源索引、证据与候选素材底座

先计算来源哈希并查找可验证缓存。默认使用本地提取；用户对当前文件明确授权 MinerU 上传时，按 `references/mineru-source.md` 调用精准解析 VLM，随后立即 cache、normalize 和 index。远程模式的 token 只从环境变量读取，CLI 不接受 token 值；没有授权、密钥或完整结果时回退本地解析。

系统对每个焦点来源只做一次完整读取，至少识别问题、缺口、目标、方法、核心结果、验证、贡献、边界，以及关键数字、单位、图、表和公式。先用紧凑来源索引选择风险页和候选证据，再按页、块、类型或候选 ID hydrate。共同产出或更新 `source-manifest.json` 与 `evidence-index.json`，再按 profile 生成分析资产：

- `final_defense`：精简的 `thesis-analysis.json`，以及入选论文图片、`figures.manifest.json` 和由其生成的 `论文图片说明.md`；
- `proposal_midterm`：`milestone-analysis.json`；开题记录计划、前期基础、验证路径、风险与里程碑，中期分开保存已批准计划基线、带日期的实际进展、偏差、风险和下一阶段行动；
- `group_meeting_literature`：`paper-index.json`，并在 `assets/papers/<paper-id>/` 下分别保存焦点论文的图片清单、图片说明、表格和公式索引；
- 所有 profile 均为实际需要的学校品牌、出版信息或其他外部来源建立可检索记录。

这一阶段只做忠实索引、定位、说明和质量标记。不得提前批量裁白边、增强、拆图、重绘图表、编译全部公式或制作装饰素材。小型焦点文献集可以索引全部清晰图件；所有项目都只把中心图、入选图或用户明确要求交付的完整图集落地到正式资产目录。来源内部或来源之间的矛盾保留所有版本和位置，不静默修正。

MinerU API 缓存默认只保留 normalizer 所需的最小 raw 白名单；完整 raw 只有显式 `--retain-full-raw` 调试 opt-in 才保留。无论采用哪种保留策略，agent 都不得直接读取供应商 raw、复制进项目资产或把它作为 deck spec 的数据结构。进入证据索引的只能是 retrieve CLI 已 hydrate、已定位、与当前主张相关的短块和候选资产引用。

核心主张必须能指向 PDF 页码、图表号、公式号、数据、项目记录、DOI 页面或可靠外部来源。开题的假设、计划与预期成果不得写成既成结果；中期的“计划—实际”必须同时引用基线与进展证据。文献组会必须区分论文作者的结论、汇报者的综合与汇报者的批判。尚无证据的内容只能作为假设、讨论问题、边界或待办。

## 3. 叙事、逐页规格与大纲

先读取匹配的 profile reference，再建立主线、选择页面和布局。毕业答辩让结果与验证构成主体；开题围绕“为何值得做、要回答什么、如何获得证据、为何可行”；中期围绕“原计划是什么、实际完成什么、偏差为何、如何收敛”；文献组会围绕“为什么值得读、证据说明什么、是否可信、对本组有什么启发”组织。方法只保留理解结果所需的信息。章节数量、目录页、章节过渡页、论文分隔页和导航方式由叙事决定，不采用固定五或六部分，也不按模板或论文数量复制固定章节结构。

每页只执行一次以下决策链：

```text
评委问题
→ 一句话结论
→ 支撑证据
→ 最快且真实的表达形式
→ 适合该证据关系的布局或自由画布
→ 精简上屏文字
→ 自然发言稿与过渡
→ Sources
```

由 story owner 生成 `deck-spec.json` 作为完整机器事实源，再用 `scripts/build-deck-map.mjs` 生成导航级 `deck-map.json`，并由 deck spec 生成 `PPT内容与设计大纲.md`。局部修订优先读取 deck map 和目标页规格，不重新加载完整 deck spec。公式和流程图只有在实际使用、或确有必要记录否决理由时才写入对应字段；普通页面省略未使用字段，不生成长篇“不需要”的解释。

毕业答辩规格必须在首次构建前先通过两类门禁：

- 结构门禁：正式答辩默认 3–6 个主章节，每个主章节有且仅有一张章节首页；章节名来自论文问题与证据主线，不使用“问题与路线”、“答辩备查”等生产内部语言。备查材料位于结束页之后，不进目录、不进导航、不单独设章节首页。
- 科学设计门禁：每张技术页先声明 `relationship_topology`、`visual_focus`、`annotation_plan` 和必要的 `asset_transform`，再将其落实为实际渲染的图、标注、强调或可编辑关系。声明这些规划字段不等于已落实。分支/汇合/反馈不得使用线性流程版式；密集科研图必须选择直接标注、拆图、局部放大或忠实重绘，不得只做 contain 后缩到双栏。

若 `workflow_mode=outline_first`，在大纲生成后等待用户；否则直接进入构建，不二次确认。

## 4. 入选资产、公式与成品构建

只加工已经进入 `deck-spec.json` 的规范资产 ID，保持 processed ID 集合是 selected ID 集合的子集；同一入选资产可因已记录的兼容或版式需要产生少量 `ready/` 变体。用户明确要求交付完整忠实图集时，把该图集作为显式选择集记录，而不是默认全量加工：

- 原始素材保持不变，裁切、标注、拆分、重绘和兼容转换写入对应来源的 `ready/`；
- 数据图表保留可复核的数据与计算；
- 简单关系图使用可编辑 PowerPoint 形状，复杂关系图选择可靠图形工具；
- 页面没有自然匹配的注册布局时，使用自由画布或项目专属构图，不强套模板。

构建前运行 `node scripts/audit-production-budget.mjs --project-dir <内部项目目录> --strict`，检查入选引用、`ready/` 变体、孤儿加工文件、deck map 体量和重复全稿预览。审计只报告和阻断，不删除文件；合法的原始素材回退必须有显式理由。发现未入选的 ready 资产时，停止继续加工，并在构建前移出正式 ready 集或记录合法保留理由，不为“以后也许会用”扩充资产库。

文献组会的论文快照只显示已核验且对当前叙事有用的字段。标题、作者、发表来源、年份、DOI/URL 和文章类型来自论文或可靠出版页面；影响因子与分区仅在确有用途、标明评价体系和年份并能复核时使用。不得把布局库中的示例刊名、作者、日期、关键词、指标或截图带入正式 PPT。

公式统一按 `references/asset-preparation.md` 的单一链路处理，并优先调用 `scripts/render-formula.mjs`。只编译入选公式；最多一次合理的 LaTeX 引擎切换和一次 SVG→PNG 切换，不建立无限回退树。复杂核心公式无法可靠呈现时停止并报告，不把 raw LaTeX 当普通文本输出。

完成资产引用后，按 `deck-spec.json` 的 profile 选择对应资产库。正常路径运行：

```bash
node scripts/build-project.mjs \
  --spec <deck-spec.json> \
  --output-dir <internal-build-dir> \
  --stem <短题名_汇报类型> \
  --render
```

它使用同一规格一次生成可编辑 PPTX、精简 Word 发言稿和同名 MJS，并只渲染一份内部 QA 预览。规格、入选资产和核心渲染代码未变时，签名缓存直接复用三个产物；先合并同一批局部修改，再调用一次构建器，不要每改一行就全量构建。局部内容修复先用 `retrieve-source-evidence.mjs` hydrate 相关页或证据 ID，再只重建和检查目标页及衔接页。只在定向调试时才分别调用 `build.mjs`、`build-speaker-script.mjs` 或 `create-project-builder.mjs`。

项目内容写入 `deck-spec.json`，不要临时生成数百行的项目专用 spec builder、图片提取器、联系表或交付清洗脚本。只有稳定共享组件确实缺少能力时，才修改 Skill 级脚本并加入回归测试。

项目 MJS 嵌入最终项目规格、只引用 `assets/` 相对路径，默认同时重建同名 PPTX 与 DOCX，不读取客户包之外的 deck spec。客户项目 MJS 必须显式标记 `artifact_purpose: production`；`layout_gallery` 仅允许通过底层构建器生成内部布局库，不进入项目 MJS 和交付暂存链路。

中期“计划—实际”页必须覆盖计划基线和当前进展证据；组会多篇比较页的来源必须覆盖参与比较的每篇焦点论文。

## 5. 一次完整 QA、针对性修复与最小交付

执行 `references/qa.md`：

1. 运行 schema、语义、构建和溢出检查；
2. 第一次且唯一的常规全稿视觉 QA：渲染全稿，先看联系表，再逐页全尺寸检查；
3. 修复学术错误、证据断裂、不可读内容、损坏媒体、错误品牌、遮挡、裁切和异常换行；
4. 局部修改后的证据读取、构建和人工复查只聚焦受影响页及其前后衔接页；若工具只能整稿导出，允许使用第二次完整 render，但不再次通读无关来源。主题、字体、母版、全局间距、导航或渲染器变化也只能使用这一次剩余的完整 render；
5. 硬失败为零、重要问题已修复或明确披露后停止。

默认只进行一轮完整检查和一轮针对性修复，完整 render 的绝对上限为两次。第二次后仍有硬失败时记录缺陷和阻断原因并报告，不得进入第三次整稿循环；也不得转而反复微调字距、像素相似度、轻微留白、无害元数据或其他不影响理解与交付的细节。若冷启动任务反复超过约 30 分钟，优先定位重复读取、临时脚本、全量素材加工、多次整稿渲染或交付扫描误报，不得以“继续优化”代替根因修复。

完成内部 PPTX 和 Word 的渲染检查后读取 `references/delivery.md`。调用 `scripts/stage-delivery.mjs`，由同名项目 MJS 在空白暂存目录一次重建 PPTX 与 Word，再通过白名单生成客户包。客户包根目录只能包含：`短题名_汇报类型.pptx`、`短题名_汇报类型.mjs`、`短题名_汇报类型_发言稿.docx` 和 `assets/`。名称不加入姓名、日期、版本、`final` 或“最终版”；姓名、导师、学号等已知身份词作为 forbidden terms 参与检查。

`project-config.json`、原始 `deck-spec.json`、大纲、证据索引、分析 JSON、QA 记录、预览、日志和源 PDF 均留在内部工作区。论文图片说明可随 `assets/figures/` 交付；其余素材仅保留本稿实际使用或该 profile 明确要求交付的内容。用户要求不部署时，不复制到 Codex Skills 目录，也不安装或注册。
